# 第一阶段：上传录音到笔记

日期：2026-11-13。范围：上传录音（可带 PDF 课件）到笔记显示在课堂页，这一条路走通。

## 为什么做、做到什么程度

前端（`src/`）一直跑在示例数据上（`USE_MOCK: true`）。这一阶段做最小的闭环：学生上传一段课堂录音，后端转写、写笔记，前端把 `USE_MOCK` 改成 `false` 就能在课堂页看到。同时把每堂课的成本记下来，回答 `reference/INTEGRATION.md` 第 10 节的定价问题。

**做到**

- 11 个接口：`POST /session`、`GET /home`、`POST /courses`、`POST /lectures`、`POST /lectures/:id/recording`、`POST /lectures/:id/slides`、`POST /lectures/:id/finish`、`GET /lectures/:id/status`、`POST /lectures/:id/retry`、`GET /lectures/:id`、`DELETE /lectures/:id`。
- 处理流程：存文件 → 转码 → 转写 → DeepSeek 写笔记 → 校验 → `ready` 或 `failed`。
- 每堂课的成本日志（音频分钟、token、估算美元），以及汇总脚本。
- 两家转写服务，加一个用真实录音对比它们的脚本。
- 契约测试（回复的形状对得上 `src/types.ts`），以及转写服务和写笔记模型都换成假实现的流程测试。

**不做（后面的阶段）**

- 现场录音的分段上传、Catch me up、录音回放（本阶段 `detail` 不带 `audio`，前端不显示播放器）。第二阶段已做。
- 编辑笔记、分享、学习进度、复习包、课程管理、搜索、课后补传课件。
- 会员方案、付款、正式登录。

**算失败的情况**：接口形状和前端对不上；上传中断后留下残缺文件；同一堂课被重复扣费（重试重新转写、`finish` 被调用两次各跑一遍）；模型写出的东西不合规矩却被标成 `ready`。

## 考虑过的做法

**写笔记：一次调用 vs. 分段调用。** 一堂 90 分钟的课转写下来约 2 到 3 万 token，DeepSeek V4 的上下文是 100 万，一次调用就能装下整堂课和课件。分段调用（先分主题，再逐段写要点）能并行，但要多一轮协调，主题边界也容易对不齐。选一次调用；以后真的超时或质量下降再拆。

**课件：直接给模型 PDF vs. 先抽文字。** DeepSeek 的接口对 PDF 的支持没有明确文档。所以先用 `pdfjs-dist` 逐页抽出文字，按“Slide n: 文字”给模型，用来判断要点属于哪一页、`off`（课件上没有）是否成立。缩略图本阶段不做（`slide.image: null`，前端显示页码和标题）。

**逐字稿：让模型输出 vs. 直接用转写结果。** 让模型把逐字稿再写一遍，既贵又可能改字。所以 `detail.transcript` 直接由转写的词和时间戳切成句子；模型只写要点、分节、提示、闪卡和测验。

**大文件上传：Hono 的 `parseBody` vs. 流式解析。** `parseBody` 会把整个文件读进内存，500 MB 的文件不行。所以用 `busboy` 边收边写临时文件，收完整了再改名放到位；请求中断就删掉临时文件。`Content-Length` 超过上限的请求直接回 413，不读请求体。

## 接口行为

通用：

- 所有路径在 `/api` 下（前端 `API_BASE: "/api"`）。出错一律回 `{ "message": "..." }`，这句话会直接显示给用户。
- JSON 请求体最大 64 KB，超过回 413（包括不用登录的 `POST /session`）。上传文件的请求最长可以持续 3 小时（Node 默认 5 分钟，慢网速传 500 MB 会被切断）。
- 分享页的 `GET /shared/:id` 不用登录，本阶段一律回 404 和说明（不能回 401，否则前端会让读者“重新登录”）。
- 除 `POST /session` 外都要 `Authorization: Bearer <token>`，token 无效或缺失回 401。
- 别的用户的课程和课堂一律当作不存在，回 404。
- 文件超过 `MAX_UPLOAD_MB`（默认 500，和前端一致）回 413。

| 接口 | 行为 |
|---|---|
| `POST /session` `{inviteCode, name}` | 码不对回 401 加说明（前端对这个公开接口原样显示）。给了 `name` 就更新名字。回 `{token, user}` |
| `GET /home` | `user`、`courses`、`lectures`（新的在前）、`upcoming`（从笔记里带日期的考试和截止提示汇总，只给今天及以后的）、`settings`、`usage`、`today`（按 `APP_TIMEZONE`，默认香港）。`week` 本阶段不给 |
| `POST /courses` `{code, name}` | `code` 必填，最长 20 字；`name` 最长 80 字。回 `course`，带一个配色 |
| `POST /lectures` `{courseId, title, language, source}` | 检查课程、语言、来源。`record`、`tab` 先查当天现场录音分钟数，超了回 429 加说明；本阶段还不收分段，所以再回 501“录音功能还没开放，请上传录音”（不让前端开始录一堂存不下来的课）。**第二阶段**：`record`、`tab` 照常建课（`LIVE_RECORDING=off` 时仍回 501），分钟数也算上正在录的课。`link` 回 501。`upload` 建课，状态 `recording`（和示例数据一致），回 `lecture` |
| `POST /lectures/:id/recording` | 只在 `recording` 状态收。流式收完用 `ffprobe` 确认有音轨，没有就删掉并回 415。存成固定的文件名 `recording`（不带扩展名），这样 ffmpeg 按内容识别格式，上传的文件名改不了它的读法（比如把文件叫成 `.m3u8` 当播放列表读）。同一堂课再传一次会覆盖。**第二阶段**：现场录音的课回 409 |
| `POST /lectures/:id/slides` | 在 `recording` 或 `failed` 状态收（失败后补上课件再重试）。检查 `%PDF` 文件头，不是 PDF 回 415。笔记已生成后再传（补传课件）本阶段回 409 加说明；这个检查放在文件收完之后，免得浏览器还在发送时就收到回复，把它当成网络错误 |
| `POST /lectures/:id/finish` `{duration}` | 幂等：已经是 `processing` 或 `ready` 就原样回状态，不重复排队。没收到录音回 409“这堂课没有收到录音”。否则设 `processing` 并排队。**第二阶段**：现场录音的课要收到过第一段，见下 |
| `GET /lectures/:id/status` | `{status}` |
| `POST /lectures/:id/retry` | 只在 `failed` 时排队重跑，其他状态原样回。已转写过的不再转写，只重跑写笔记 |
| `GET /lectures/:id` | `{lecture, detail}`，笔记没好时 `detail: null`。**第二阶段**：`detail.audio` 是回放链接 |
| `DELETE /lectures/:id` | 删记录、文件、笔记、成本以外的一切；正在跑的流程会被中止，跑完的结果丢掉。上传进行中被删，收完的文件也会被丢掉。成本日志保留（课堂 id 留着，用来算账） |

`lecture.duration` 用转码后音频的实际长度（`ffprobe`），不用前端传的计时。`lecture.date` 是显示用的文字：当天是 `Today`（中文界面会翻译），否则如 `Tue 10 Nov`。

## 处理流程

在服务进程里跑一个队列（并发数 `PIPELINE_CONCURRENCY`，默认 2）。服务重启时，状态还是 `processing` 的课会重新排队。每一步的结果都存下来，重试时跳过已完成的步骤：

1. **转码**：`ffmpeg` 把录音（视频则抽音轨）转成单声道 AAC 48 kbps 的 `audio.m4a`，带 faststart，可以拖动进度。这个文件用来转写，也用于回放（第二阶段）。记下时长和文件大小（第 10 节要“转码后的回放文件每小时多大”）。
2. **转写**：`Transcriber.transcribe(audio.m4a, language)` 返回带时间戳的词。原始返回存成 `transcript.raw.json` 方便对比，切好的句子存进数据库。切句：遇到句末标点且这一句超过 3 秒、停顿超过 1.2 秒或一句超过 25 秒就断开；中日韩字符之间不加空格。
3. **课件**：有 `slides.pdf` 就逐页抽文字。读不了（加了密码、文件损坏）就不用课件，照常写笔记，不让整堂课失败。
4. **写笔记**：`NotesWriter.write(...)` 把课程、标题、日期、语言、时长、带秒数的逐字稿、课件文字交给 DeepSeek（JSON 输出模式、流式、开思考），要回 `sections`、`slides`、`alerts`（带 `date`）、`flashcards`、`quiz`。回复逐项读：数字写成字符串、`"true"`、用字母表示的答案都接受；某一项实在用不了（要点没有时间或文字、闪卡没有答案）就只丢这一项。整份回复不是 JSON、或者一个能用的要点都没有，才把错误告诉模型再要一次，最多两次。
5. **整理和校验**：时间夹到 `[0, 时长]` 并取整；`section` 按时间排好、首尾相接、最后一段到时长为止；没有课件时 `slide: null`、`off: false`，`slides: []`；超出页数的 `slide` 改成 `null`；`section.slides` 由要点的页码算出（如 `Slides 3 to 6`）；`alerts.kind` 规范成 `Midterm`、`Deadline`、`Exam hint`、`Quiz`、`Final`；选项数或答案下标不对的测验题丢掉；中文解释转出另一种字体；逐字稿按 `t` 排序。最后用和 `Detail` 类型绑定的 zod schema 校验，不过就是 `failed`。
6. 存 `detail`，带日期的提示存进 `upcoming`，状态改 `ready`。

任何一步出错：状态 `failed`，错误原因记在数据库（不给前端看），日志里打印。

调用转写服务和 DeepSeek 时，只重试对方明确拒绝的（429、5xx）和根本没送到的（连不上）。超时、回复读到一半断掉这类情况不重试：音频可能已经送到并计费，再试一次就付两次钱。

## 成本日志

表 `costs` 每一步一行：课堂 id、步骤（`stt`、`notes`）、服务商、模型、音频秒数、输入 token（命中缓存和未命中分开）、输出 token、其中思考 token、估算美元、时间。单价写在 `.env`，默认值取自各家价目页：Scribe 和 Deepgram 按小时；DeepSeek 按百万 token，并且分高峰（UTC 周一到周五 01:00–04:00、06:00–10:00）和非高峰半价。

`npm run costs` 打印每堂课的成本，以及“每小时录音的转写成本”“按 90 分钟算每堂课的笔记成本”“有课件和没课件的差”“回放文件每小时多大”，对应第 10 节的表。中文解释多出来的成本：`ZH_EXPLANATIONS=off` 跑同一堂课对比。

# 第二阶段：现场录音、Catch me up、回放

日期：2026-11-14。范围：`reference/INTEGRATION.md` 第 2、4、5 节里录音和回放的部分。

## 做到什么程度

**做到**

- `POST /lectures` 的 `record`（麦克风）和 `tab`（网课）可以用了。
- `POST /lectures/:id/chunks`：收分段，按（课堂, `seq`）去重，回实时逐字稿和考试提示；录音中途也执行每日分钟上限。
- `POST /lectures/:id/finish` 支持现场录音，包括“用已保存的部分写笔记”和 `retry`。
- `POST /lectures/:id/catch-up`。
- 回放：`detail.audio.url`（带签名的链接，支持 HTTP Range），以及 4.4 的 `keptUntil` 和 `expired`（`AUDIO_KEEP_DAYS`，默认不用）。
- `npm run costs` 多了实时转写和 Catch me up 两项；`npm run compare-stt -- --chunks 15` 按实时的做法转写，和整段比。

**不做**

- `attachLink`（视频链接）仍回 501。要从各个视频网站把录音下载下来，牵涉版权和网站条款，依赖 yt-dlp 这类经常随网站改版失效的工具，和现场录音也没有共用的部分。等确定要支持哪些网站（学校的 Panopto、YouTube……）再做。
- 分享页的录音（4.3）：分享是第三阶段，默认不带录音。
- 用 WebSocket 流式转写（ElevenLabs 有实时模型）：前端每 15 秒才交一段，用一段一段的普通转写就够，第一句字大约 20 秒出现。

**算失败的情况**：分段重发被存两次或付两次钱；乱序、缺段让整堂课读不出来；网络恢复后补发的一批分段让逐字稿重复；删掉的课还在转写或留下文件；上限到了以后前端卡住、结束不了录音；回放链接不用登录就能被别人猜到。

## 实测：15 秒一段的准确度

没有真实课堂录音（问过用户），用两段 macOS 合成语音测，`npm run compare-stt -- --chunks 15`，ElevenLabs `scribe_v3`：

| 录音 | 整段转写错误率 | 15 秒一轮（实时的做法） | 多送的音频 | 每轮用时 |
|---|---|---|---|---|
| 英文夹粤语，62 秒 | 4.6% | 6.1% | 13% | 1.2 秒 |
| 英文夹普通话，98 秒 | 2.5% | 3.1% | 12% | 1.1 秒 |

多出来的错误不在切口：被切开的词会留到下一轮再转写（见下），逐字对比里没有缺词或断词。差别有两种：短片段里数字写法不同（“第一至”变成“第 1 至”），以及一句粤语被写成了普通话（呢个→这个，唔→不，嘅→的）。15 秒太短，模型判断不准是哪种中文，而粤语夹英文正是主要用户。

**决定：笔记用录音结束后整段重新转写的结果；实时转写只用于录音页（实时逐字稿、考试提示、Catch me up）。**

- 代价：转写付两次钱。实时 1.12 倍加整段 1 倍，是上传录音的 2.12 倍；按 `scribe_v3` 每小时 0.20 美元算，现场录音每小时转写 0.425 美元。这就是第 10 节要的“实时转写与课后一次性转写的成本差”，端到端实测也是 2.12 倍。
- 好处：上传和现场录音写笔记走同一条路；实时转写有几轮失败（网络、服务商出错）也不影响笔记。
- 合成语音比真实课堂干净。拿到真实录音后请再比一次（`npm run compare-stt -- --language en-yue --chunks 15 录音.m4a`）。如果差别很小，可以改成直接用实时结果写笔记，省一半转写费。

## 分段怎么存、怎么读

用 Chrome 的 `MediaRecorder` 实测（和前端同样的码率和切法）：

- **分段不能单独读。** webm 只有第一段带文件头，后面每段都从一个 cluster 中间开始。Chrome 的 MP4 第一段只有文件头，一点声音都没有，第二段才有声音。
- 每段存成一个文件 `chunks/000123`，数据库 `chunks` 表以（课堂, `seq`）为主键，重发的那段不再存。
- 读的时候用 ffmpeg 的 concat 协议，把第 0 到 k 段当成一个文件，用 `-ss` 跳到要的位置。ffmpeg 跳过前面的部分只读不解码：在一个 90 分钟的 webm 里跳到最后 15 秒只要 0.07 秒，整段解码要 7 秒。跳转位置 webm 精确到采样，MP4 差 10 毫秒以内。文件名用相对路径，所以 4 小时的课命令行也很短（Linux 一个参数最长 128 KB）。
- 到了一半的文件（最后一段停在 cluster 中间）ffmpeg 照样读到能读的地方，不报错。
- 结束时，按 `seq` 顺序拼成 `recording`，转成 `audio.m4a`（和上传一样），然后删掉分段。
  - 缺了中间某段：用 `aresample=async=1` 补成静音，后面的时间不变（webm、MP4 都实测过）。
  - 缺了第一段：读不出来，`finish` 回 409。
- 一堂课的分段总量受 `MAX_UPLOAD_MB` 限制，单段受 `MAX_CHUNK_MB`（默认 10）限制。Chrome 的 MP4 不管码率设置，实测约 105 kbps，所以上限要留宽。

## 实时逐字稿

每收到一段，跑一“轮”：

1. 只看按顺序到齐的分段（缺了第 k 段，就等它到了再往后读）。
2. 从上一轮停下的地方切到已到音频的末尾，送 Scribe。新音频不到 5 秒就等下一段。
3. 结束时间在最后 2 秒之前的词才留下。最后 2 秒下一轮连同新音频再转写一次，被切开的词因此不会写错。下一轮从两个词之间的空隙中间开始。
4. 下一轮开头如果重复了上一轮最后一个词（1 秒以内），就丢掉：端到端实测里，粤语一字一词时，一个字的尾音在下一轮又被听成同一个字。
5. 一轮通常停在一句话中间。最后一个句末标点之后的词先不送，存在数据库里（`live_held`），下一轮接上新词一起送，所以录音页看到的是整句（端到端实测前后对比：之前每两三行就有一句被切成两行）。这半句的字因此晚一轮出现；一句话超过 30 秒还没结束就照送。Catch me up 会带上这半句。
6. 粤语课和整段转写一样转成繁体。存成行，找考试提示，记成本（`costs` 表 stage `live`）。

规则：

- 每堂课同时只跑一轮；跑的时候来的新段，由下一轮一起处理（网络恢复后一下子补发的十几段，不会变成十几轮）。所有课堂同时跑的轮数有上限（`LIVE_CONCURRENCY`，默认 4）。
- 分段的回复最多等这一轮 8 秒（`LIVE_REPLY_WAIT_MS`），等不到就先回空数组，字随下一次回复一起送（INTEGRATION 第 5 节允许）。端到端实测：开始录音后约 20 秒出现第一句（录音页写的是“大约半分钟”）。
- 回复里的行记下是随哪个 `seq` 的回复送出的。同一段重发（上次的回复丢了）时，回复和上次一样，不会漏字，也不会重复。
- 进度全在数据库和分段文件里，服务重启后，下一段来时从上次停下的地方继续。
- 某一轮转写失败：不马上重试，下一段来时连同这段一起转写，没送到的不算钱。服务商长时间不可用、积压超过 120 秒时，只转写最近 30 秒，实时逐字稿跳过中间这段，笔记照样完整。
- 转写服务把每一轮的第一个词当句首大写，接在半句后面时会出现“the Demand curve”。只影响录音页；要改成小写就得猜专有名词（Keynes、November），没有改。
- **实时考试提示用关键词，不用模型**：midterm、final exam、quiz、due next Friday、deadline、期中、期末、測驗、交功課、考試……命中的那一行原样弹出，`kind` 用前端会翻译的五个词，同类提示两分钟内只弹一次。不花钱，没有延迟，弹出的是老师的原话。漏掉或误报只影响录音页，笔记里的提示是课后由模型写的，带日期。
- `LIVE_TRANSCRIPT=off`：不做实时转写，录音页没有字，Catch me up 回 501；每段只量一下长度，用于分钟上限。第 10 节提到可以只在付费版提供实时逐字稿和 Catch me up，这个开关就是为此准备的（按用户区分要等第四阶段）。

## 每日分钟上限

- **开始录音时**（第一阶段已有）现在也算上正在录的课已收到的音频，两台设备不能各开一堂超出上限。`GET /home` 的 `usage.minutesToday` 同样包括正在录的课。
- **录音中途**，难处在前端：它只在开始前检查；分段回复里的错误说明不会显示；除了 404 和 410，分段出错都会留在队列里一直重试。所以：
  - 剩 5 分钟时，这一段回复的 `alerts` 里放一条 `{kind: "Recording", text: "About 4 recording minutes are left today. ..."}`，录音页会像考试提示一样弹出（`Recording` 这个词会被翻译）。
  - 用完的那一段照收，回复里放一条“今天的分钟用完了，已停止保存，结束录音就能用已保存的部分写笔记”。之后的段回 410，前端就不再发这堂课的分段；结束录音时照常调 `finish`，用已保存的部分写笔记。
  - 不能回 429：前端会把这段留在队列里不停重试，结束录音时会卡在“Waiting for a connection”，下次打开页面也补发不出去。
- 分钟数按课堂开始那天算（和第一阶段一样）。

## finish、“用已保存的部分写笔记”、retry

- 现场录音的课 `finish`：至少收到过第一段，否则回 409“没有收到这堂课的音频”。停掉实时转写，设 `processing` 并排队。流程多了第 0 步“拼接分段”，其余和上传一样。仍然幂等。
- 页面被关掉的课一直是 `recording`，分段一直保留（4.2 第 5 条）。学生点“Make notes from what was saved”时，前端先补发本机剩下的分段，再调 `finish`（`duration` 0，不记）。
- `finish` 之后再来的分段：收到过的回 200 空数组（前端把它从本机删掉），新的回 410（不会加进已经在写的笔记）。
- `retry`：拼好的录音已经在就不再拼；失败发生在拼接之前，就从分段再拼。
- 删除正在录的课：停掉这一轮，结果不存，文件删掉；之后的分段回 404。

## Catch me up

- 取最后 5 分钟的实时逐字稿（以已收到音频的末尾为准）。先等一轮把最新的音频转写完（最多 8 秒）。
- 交给 `deepseek-flash`（不开思考，`CATCHUP_MODEL` 可改），要 2 到 4 句英文，只写逐字稿里有的内容。
- 实测一次约 1000 输入 token、不到 100 输出 token，0.0001 到 0.0003 美元（第 10 节“每点一次的成本”）。成本记在 `costs` 表，stage `catchup`。
- 还没有任何字：直接回一句“还没有可以总结的内容”，不调模型。模型出错回 502 加说明，前端会显示。

## 回放

- `detail.audio.url` 是带签名的链接 `/api/lectures/:id/audio?exp=…&sig=…`（HMAC-SHA256，密钥第一次用时生成，存在数据库，重启后链接仍有效），12 小时有效（`AUDIO_LINK_HOURS`）。
  - `<audio>` 发不了 token，所以链接本身就是凭证，别人猜不到。
  - 过期、被改过、换到别的课堂上都回 403。前端播放出错时会重新拿一次课堂（4.2 第 3 条），拿到新链接。
  - 设了 `PUBLIC_URL` 就给完整地址，否则给相对路径（前端和 API 在同一个地址时就是这样）。
- 文件是 `audio.m4a`（AAC 48 kbps 单声道，faststart），支持 Range：206、416、`HEAD`。端到端实测在 Chrome 里能加载，并跳到任意位置。转码后每小时约 21.4 MB。
- 下载：`Content-Disposition: inline`，文件名用课堂标题。
- `detail` 只在 `ready` 时有，所以只有写好笔记的课有回放。

## 录音保留期限（4.4）

- `AUDIO_KEEP_DAYS` 默认 0，表示全部保留，不给 `keptUntil`，和 4.4“现阶段录音全部保留，这些字段都不用给”一致。
- 设成 N 天：
  - `keptUntil` 是上课当天（`APP_TIMEZONE`）加 N 天；
  - `GET /home` 的 `usage.audioDays` 是 N；
  - 启动时和之后每 6 小时，删掉过期的录音（`audio.m4a`、`recording`、分段），`detail.audio` 变成 `{expired: true}`，笔记照常。
  - 只删 `ready` 的课：`failed` 和没录完的课还要靠录音写笔记（4.4）。
- 按会员等级区分天数要等第四阶段。

## 数据库

- 新表：`chunks`（收到的分段）、`live_lines` 和 `live_alerts`（实时逐字稿和提示，记着随哪个 `seq` 送出）、`meta`（回放链接的密钥）。
- `lectures` 加列：`live_from`（下一轮从哪一秒开始）、`live_audio`（已收到的秒数）、`live_held`（还没说完的半句）、`live_limit`（0、1 已提醒、2 已停止）、`chunk_bytes`、`audio_expired`。
- 第一阶段的数据库启动时自动加列，不用迁移脚本。

- 真的 ffmpeg 加真的 Chrome 分段（`test/fixtures`，webm/Opus 和 MP4/AAC 各一套）：任意位置切出一段、到了一半的分段、乱序和重发后拼出的录音逐字节一致、长度对、faststart、缺段补静音后长度不变、Range。
- 回放：签名、过期、改过的链接、别的课堂、删掉的课、`PUBLIC_URL`、Range 的几种写法、保留期限和清理。
- 端到端（不在 `npm test` 里，花钱）：构建好的前端在 Chrome 里，用假麦克风播录音（Chrome 的 `--use-file-for-fake-audio-capture`），服务在 8788 端口、用单独的数据目录，ElevenLabs 和 DeepSeek 都是真的。三次：

  | 录音 | 结果 | 花费 |
  |---|---|---|
  | 62 秒英文夹粤语，录完写笔记 | 开始后 20 秒出现第一句；Midterm 提示弹出；Catch me up 三句总结都对；结束后 97 秒笔记写好（6 节，3 条提示）；回放能加载并跳到 62.9 秒 | 0.027 美元（实时转写 0.0042，整段 0.0038，笔记 0.0192，Catch me up 0.0001） |

  | 同一段，改了“半句留到下一轮”之后，录完丢弃 | 录音页每行都是整句；丢弃后课堂和文件都删掉 | 0.006 美元 |

顺手修了第一阶段的两个问题，都在 `src/http/upload.ts`：

- `MAX_UPLOAD_MB` 带小数时（如 0.3），超过上限的文件会被截短，然后当成完整的文件收下（busboy 只在字节数正好等于上限时报超限）。现在上限按整字节算（加了测试）。
- 上传中途被拒（超限、断开）时，临时文件有时删不掉：写文件的流还没打开文件就被停下，删除之后它才把文件建出来，`data/tmp` 里留下一个 `.part`（重启时才清）。已有的上传测试连跑 20 次有 6 次碰到。现在等写文件的流关掉再删，改后连跑 25 次没再出现。
